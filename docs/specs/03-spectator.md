# 仕様 03：観戦機能と「参加／観戦を選ぶロビー」

ブランチ：`feature/spectator`
前提：CLAUDE.md、仕様01・02で入った基盤（`turnOf` / `room` 引数 / `onConnectionChange` / `ctx.prev` / `ctx.sound` / `.g-layout` / `lib/readyCheck.js`）。
**最初に `server.js` と `public/app.js` の現状を読み、この仕様の名前と実際のコードの名前が違う箇所は、実際のコードに合わせて読み替えること。** 読み替えた箇所は最後の報告に書く。

## 1. やりたいこと（要件）
1. ゲーム中に部屋へ入った人は **観戦者** になる
2. ゲームが終わったらロビーに戻り、各自が **参加** か **観戦** かを選ぶ
3. 観戦者も含めた **全員が準備OK** になったら開始する
4. きゅうり・インディアンポーカーで **脱落した人** も、観戦者と同じ画面で続きを見られる（ババ抜きで上がった人も同じ扱い）

## 2. 決めごと
| 項目 | 決定 |
|---|---|
| 観戦者に見える情報 | 部屋の設定で切り替える。**既定は「公開情報のみ」**。ホストがロビーで「観戦者に全員の手札を見せる」をオンにできる |
| 「公開情報のみ」の意味 | **プレイヤー全員が見えている情報だけ**。誰か1人にでも隠れている情報は見せない（例：インディアンポーカーの宣言中のカードは全部伏せる） |
| なぜ既定を「公開情報のみ」にするか | 通話しながら遊ぶ前提なので、観戦者（脱落者を含む）が手札をうっかり口にするのを防ぐため |
| 脱落者・上がった人 | 観戦者と同じ見え方になる（同じ設定に従う）。自分の席は「自分」として強調する |
| 開始のしかた | 条件がそろったら **3秒カウントダウン** の後に自動で開始。誰かが準備OKを取り消すか、入退室があるとカウントダウンは止まる |
| ホストの強制開始 | 参加人数が条件を満たしていれば、ホストは準備OKを待たずに開始できる（確認ダイアログあり）。切断した人を待ち続けて詰まるのを防ぐため |
| 部屋の上限 | 参加者はゲームの `maxPlayers` まで。観戦者を含めた部屋全体は **16人** まで |

## 3. 基盤（server.js）

### 3-1. 部屋のメンバー
`room.players` を **`room.members`** に置き換える。
```
member = { id, token, name, socketId, connected,
           role: 'player' | 'spectator',   // ロビーでの選択
           ready: boolean }                // ロビーでの準備OK
room   = { code, gameId, hostId, members, phase: 'lobby'|'playing'|'finished',
           state, gamePlayerIds: string[],          // 今のゲームに参加している人（開始時に確定）
           settings: { spectatorSeesAll: false },
           countdown: { endsAt, timer } | null, notice, lastActive }
```
- 入室したときの role：
  - ロビー中：参加者がまだ `maxPlayers` 未満なら `player`、満員なら `spectator`
  - ゲーム中（playing / finished）：必ず `spectator`
- 入室を断るのは、部屋全体が16人のときだけ（ゲーム中でも入れる）
- ゲームが終わってロビーに戻るとき：全員の `ready = false`。role は前回の選択を残す。ゲーム中に観戦で入った人は、参加者に空きがあれば `player` にする

### 3-2. ロビーのイベント（socket）
| イベント | 誰が | 処理 |
|---|---|---|
| `lobby:role` `{ role }` | 本人 | ロビー中だけ変更できる。`player` にしたことで `maxPlayers` を超える場合は `{ error: '参加者が満員です（最大N人）' }` を返す。変更したら本人の `ready = false` |
| `lobby:ready` `{ on }` | 本人 | 準備OKの付け外し |
| `lobby:settings` `{ spectatorSeesAll }` | ホスト | 設定を変更する。変更したら **全員の `ready = false`**（条件が変わったので確認し直す） |
| `lobby:forceStart` | ホスト | 参加者数が `minPlayers`〜`maxPlayers` なら、準備OKを待たずに開始する |
| （削除）`game:start` | — | `lobby:forceStart` と自動開始に置き換える |

### 3-3. 自動開始の判定 `checkLobby(room)`
次のどれかが起きるたびに呼ぶ：role・ready・settings の変更、入室、退室、切断、再接続。
- 条件：
  - 接続中の全メンバーが `ready`
  - 参加者（role=player かつ接続中）の人数が `minPlayers` 以上 `maxPlayers` 以下
- 条件を満たし、カウントダウン中でなければ：`countdown = { endsAt: now + 3000 }` にしてタイマーを開始し、broadcast する
- 条件を満たさなくなったらカウントダウンを止めて broadcast する
- タイマーが切れたら開始処理（3-4）
- 切断中のメンバーは「準備OK」の判定から除外する（待ち続けないため）。ただし切断中の `player` は参加者に数えず、ゲームにも入れない

### 3-4. 開始処理
- `gamePlayerIds` = role=player かつ接続中のメンバー（入室順）
- `state = game.setup(gamePlayerIds の {id, name})`
- `phase = 'playing'`、カウントダウンを解除する

### 3-5. 画面に送る情報（broadcast）
各メンバーに送る `room:update` に次を追加・変更する。
```
members: [{ id, name, connected, role, ready }],
gamePlayerIds,
you, yourRole: 'player' | 'spectator' | 'out',   // 'out' = 参加したが脱落・上がり
settings, countdownEndsAt: number | null, hostId, phase, ...
view
```
- 1人ずつの `view` の決め方：
  1. ロビー中：`null`
  2. `gamePlayerIds` に入っていて、`game.isOut?.(state, id)` が false：`game.view(state, id)`（今までどおり）
  3. それ以外（観戦者・脱落者）：`game.spectatorView(state, { seesAll: settings.spectatorSeesAll, viewerId: id })`
     - `spectatorView` を持たないゲームは `game.view(state, null)` で代用する
- `yourRole`：ロビー中は member.role。ゲーム中は 2 なら `player`、`gamePlayerIds` にいて脱落していれば `out`、それ以外は `spectator`
- `turnIds` / `yourTurn` は今までどおり。観戦者・脱落者が `yourTurn` になることはない

### 3-6. ゲーム中の入退室
- 観戦者の退室・切断：ゲームには何もしない（`onLeave` を呼ばない）
- 参加者の退室：今までどおり `onLeave`
- `game:action` は `gamePlayerIds` に入っている人だけが送れる。観戦者からは `{ error: '観戦中は操作できません' }`
  - ただし準備OK系の action（きゅうり・インディアンの `ready`）は、脱落者が送っても今までどおり受け付ける（数には入れない）
- ホストが抜けたら、次のホストは **接続中の参加者 → 接続中の観戦者 → その他** の順で選ぶ

### 3-7. ゲームが終わったら
- `phase = 'finished'` のまま結果を見せる（今と同じ）
- ホストの「ロビーに戻る」で `phase = 'lobby'`、`state = null`、`gamePlayerIds = []`、全員 `ready = false`、role の整理（3-1）

## 4. ゲーム側インターフェースの追加
`games/<id>/server.js` に次を追加する（どちらも任意だが、隠し情報があるゲームでは `spectatorView` は必須）。

| 追加 | 内容 |
|---|---|
| `isOut(state, playerId)` → boolean | 脱落した・上がった・退席した人なら true |
| `spectatorView(state, { seesAll, viewerId })` | 観戦者用の view。`viewerId` は脱落者なら本人の id（自分の席を強調する用）、観戦者なら観戦者の id（ゲーム内には存在しない） |

各ゲームの見せ方：

| ゲーム | seesAll = false（既定） | seesAll = true |
|---|---|---|
| 三目並べ | 盤面すべて（隠し情報なし） | 同じ |
| ババ抜き | 各自の枚数だけ（今の他人視点と同じ） | 全員の手札の中身 |
| きゅうり | 場・得点・各自の枚数・過去のトリック | ＋全員の手札の中身 |
| インディアンポーカー | 宣言中は **全員のカードを伏せる**。公開後は全員分を見せる | 宣言中も全員のカードを見せる |

- `isOut`：ババ抜き＝上がった人／退席した人、きゅうり・インディアン＝脱落した人／退席した人、三目並べ＝なし
- 注：インディアンポーカーでは、脱落すると（既定設定では）他の人のカードが見えなくなる。脱落者がカードを口にするのを防ぐための意図した挙動。ルール欄に1行書いておく

## 5. 画面

### 5-1. ロビー（public/）
ロビーの紙パネルを次の構成にする。
- 上部：ゲーム名・招待コード・招待リンク（今のまま）
- **自分の選択**：2択のボタン「参加する」「観戦する」（`role="radiogroup"` で、選んでいる方を強調）
  - 参加者が満員のときは「参加する」を無効にし、「参加者が満員です」と添える
- **準備OKボタン**：大きく。未押下は primary の「準備OK」、押下済みは通常ボタンの「取り消す」。自分が未押下の間は、仕様01の金色パルスで目立たせる
- **メンバー一覧**を2つに分ける
  - 「参加（2 / 7）」：名前・準備OK（✓／待ち）・ホスト・あなた・接続待ち
  - 「観戦（1）」：同じ表示
- 状態のメッセージ（1行）：
  - 人数が足りない：「あと1人、参加者が必要です」
  - 参加者が多すぎる：「参加者が多すぎます（最大N人）。だれか観戦に回ってください」
  - 待ち：「準備OK 3 / 4」
  - カウントダウン中：「3…2…1 で開始します」を大きく表示する（`countdownEndsAt` から残り秒数を計算し、0.2秒ごとに更新）。準備OKを取り消せば止まることも小さく添える
- **ホストだけに見えるもの**：
  - トグル「観戦者に全員の手札を見せる」（`role="switch"`、`aria-checked`）。説明として「オフのときは、プレイヤー全員に見えている情報だけを見せます」と添える
  - 「待たずに開始」（ghost・小さめ。押すと確認ダイアログ）
- 準備OKがそろうと `ready` 音、カウントダウン開始時に `turn` 音を鳴らす

### 5-2. ゲーム画面
- ゲームバーに状態タグを出す：
  - 観戦者：「観戦中」
  - 脱落者・上がった人：「脱落 — 観戦中」（ババ抜きは「上がり — 観戦中」）
  - 設定がオンのときは、全員に小さく「観戦者には手札が見えています」と出す（プレイヤーが知っておくため）
- `.g-side` の一番下に「観戦（N人）」の一覧を出す。基盤側で描くので、各ゲームの対応は不要。`.g-side` がないゲームでは卓の下に出す
- `ctx` に `role`（`'player'|'spectator'|'out'`）と `seesAll` を追加する
- 各ゲームの `client.js` は、`ctx.role !== 'player'` のときは次のようにする
  - 操作ボタン・手札の選択を出さない
  - seesAll のときは全員の手札を各席の下に `cardHTML(…, { cls: 'sm' })` で並べる
  - 「あなたの番」系の文言は「○○さんの番」に置き換える
- ゲーム中に観戦で入った人には、`ctx.prev` が null なので効果音を鳴らさない（今の仕組みのまま）

## 6. テスト

### 6-1. 部屋の流れのテスト（test/room.flow.js を新規作成し、npm test に追加）
`socket.io-client` で実際にサーバーを起動して確かめる（devDependencies に追加してよい）。最低限、次のシナリオ：
1. ロビーで2人が参加・1人が観戦 → 3人とも準備OK → 約3秒後に開始。観戦者の view が spectatorView になっている
2. カウントダウン中に1人が取り消す → 開始しない
3. カウントダウン中に誰かが入室する → 止まる（新しい人は準備OKでないため）
4. 参加者が満員のときに `lobby:role player` → エラー
5. ゲーム中に入室 → spectator になる。`game:action` はエラー
6. 観戦者がゲーム中に退室 → ゲームは続く（`onLeave` が呼ばれない）
7. 終了 → ロビーに戻る → 全員 ready=false、role は維持、途中で入った観戦者は（空きがあれば）player
8. 設定の変更で全員の ready が外れる
9. 切断中のメンバーは準備OKを待たれない。再接続すると待ちに戻る
10. ホストの `lobby:forceStart`（人数が条件外ならエラー）
11. ホストが抜けると、接続中の参加者にホストが移る

### 6-2. 漏洩テスト（既存のランダムテストに追加）
各ゲームのランダムテストで、毎ステップ次を検証する：
- **seesAll=false の spectatorView** をJSONにして、そこに含まれるカードが **全プレイヤーの view に共通して含まれるカードだけ** であること
  - 実装例：全プレイヤーの view から出てきたカード（`r`+`s`）の集合の「共通部分」を作り、spectatorView のカードがその部分集合であることを確かめる
- seesAll=true の spectatorView には、生きている全員の手札が含まれること
- 脱落者（isOut=true）に、基盤が `view` ではなく `spectatorView` を使うこと（基盤の関数 `viewFor(room, memberId)` を切り出してテストする）
